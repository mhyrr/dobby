Your own agent

You do not have to do the setup in Dobby's chat. Dobby serves its tools over MCP at /mcp, the same tools, the same schemas and the same refusals its own model gets, so the AI you already use can do the work.

Mint a key

On /admin, under the system section, mint a token with a label naming the agent that will hold it: Ann's laptop, the kitchen Mac. The label is what every call made with the key is logged under. The key is shown once.

…and beneath it, once: The token for Ann's laptop is ‹43 characters› — copy it now. Dobby keeps only a fingerprint, so it will not be shown again. Leave the page and the row stays; the key does not.

revoke closes the door without ceremony, and the next request with that key gets the same 401 a made-up key gets. There is no undo: the plaintext is exactly what Dobby does not keep. Mint a fresh one.

Connect your agent

For Claude Code, one command, with the machine's address:

claude mcp add --transport http dobby http://192.168.1.20:4000/mcp \
  --header "Authorization: Bearer <the token>"
Use the address, not the name Claude Code's MCP client (2.1.240, August 2026) does not resolve .local names and times out on them, where a browser on the same laptop resolves them fine. Dobby prints the address when it starts: the house answers at http://dobby.local:4000/ (192.168.1.20). Any MCP client that speaks streamable HTTP connects the same way.

What you should see

$ claude mcp list dobby: http://192.168.1.20:4000/mcp (HTTP) - ✔ Connected

What it can do

Everything Dobby's own model can. tools/list returns this house's roster, not the library's (a house with no vacuum offers no vacuum tools), and every call goes through the same device agent, with the same validation and the same words when it refuses.

confirm_device, create_schedule, delete_schedule, discover_entities, light_get_status, light_set_brightness, light_turn_off, light_turn_on, list_schedules, propose_device, set_schedule_enabled, thermostat_get_status, thermostat_set_temperature, wifi_get_status

The roster of a house with a thermostat, a light and a printer. Add a vacuum and the vacuum tools appear on the next connection.

The trust, stated plainly

A key-holder speaks for the household, the way anyone with the Wi-Fi password does on the surfaces. That includes confirming a device into the house: on this path, possession of the key is the yes. Dobby does not defend against a stolen key. That is the posture Home Assistant takes with its own long-lived access tokens, which this audience already lives with. What the key does carry is a name, and the name is the point: the activity log and every proposal say which agent asked.

A real session

This is what happened on August 22, 2026, with Claude Code pointed at a running house, asked to adopt one light. The tool calls and their results are verbatim; the prose between them is Claude's.

  • Claude

    Step 1: discover_entities.

    discover_entities → 12 entities, among them light.kitchen_lights · type light · Kitchen Lights

  • Claude

    light.kitchen_lights is listed with type light. Step 2: propose_device.

    propose_device(id light:kitchen, type light, name "kitchen lights", entity light.kitchen_lights) → proposal 1 · proposed · proposed_by "Maya's walkthrough"

  • Claude

    Proposal id 1 returned. Step 3: you've agreed to this specific proposal, so confirming it.

    confirm_device(1) → applied: true · "written to the house file; the house has taken it on"

  • Claude

    Applied. Step 4: re-discover, then read the light's status.

    discover_entities → 11 entities; light.kitchen_lights no longer among them

    light_get_status(light:kitchen) → available · on · 71% · dimmable

Notice what the house did between the third and fourth calls: the confirmation wrote the file, restarted the house, and answered only when the house was running with the new device in it. The reply says has taken it on, past tense, because it had. The agent's connection survived the restart; the next two calls went through on the same session.

Tell it what you have

"Dobby at 192.168.1.20:4000 runs my house. I have a thermostat, three lights and a robot vacuum, all on Home Assistant — set them up." The agent discovers what HA sees, proposes each device, and confirms them into the house file; the house restarts into its new shape and the cards fill in as Home Assistant speaks. The doctrine an agent is handed with the tools says the rest: discover first, copy entity ids exactly, propose before confirming, and confirm only what the person actually agreed to.
