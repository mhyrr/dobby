Developing

A real Home Assistant on your machine with virtual devices and no hardware, two test tiers that answer different questions, and a door for the agent working on Dobby rather than through it.

Two rigs

mix test and a bare mix phx.server run against the fake Home Assistant in the repository: no HA, no network, no model calls, and no environment variable changes that. That is the rig, and it is the whole application.

The second rig is a real Home Assistant in a container, for exercising the real client against actual protocol semantics: connection, authentication, subscription, service calls. It is disposable; its state is gitignored and remaking it costs two commands.

The local Home Assistant

Requires Docker. The official image runs HA directly; no HAOS VM is involved.

cd dev/home-assistant
docker compose up -d

First boot takes a minute or two, and the instance listens on http://localhost:8123, loopback only. Its configuration is configuration.seed.yaml, mounted read-only, and it enables HA's demo integration: climate devices (climate.hvac, climate.heatpump, climate.ecobee), lights, and vacuums with nothing behind them.

Initialize it once. This creates the owner account, sets US customary units (Dobby's temperature fields say Fahrenheit, and the unit system is what makes HA report in it), finishes onboarding, and mints the long-lived token Dobby authenticates with. It prints the credentials and writes them nowhere.

mix run --no-start dev/home-assistant/onboard.exs
docker compose restart   # so entities rendered before the unit change re-render in °F

Then point Dobby at it. config/homes/local.yaml is the committed house file for this rig; it binds the real client and takes its credential from the environment, which in development starts from a gitignored .env.

cp .env.example .env    # then fill in the token onboard.exs printed
mix phx.server

What you should see

[info] connected to Home Assistant 2026.8.2 at http://localhost:8123 home "local" with 4 device(s) %{ id: "thermostat:main", name: "demo thermostat", type: :thermostat, available: true, target_temperature_f: 70, min_temperature_f: 60, max_temperature_f: 76, current_temperature_f: 72, hvac_mode: :cool } … initial state sync: ok

From mix dobby.ha.verify against the rig, August 22, 2026. Running it has the round trip.

To see what the instance actually has: Developer Tools → States in HA, or

curl -s -H "Authorization: Bearer $DOBBY_HA_TOKEN" \
  http://localhost:8123/api/states | jq -r '.[].entity_id'

Credentials for HA integrations, a cloud thermostat's account or a robot's password, do not belong in .env or anywhere in the repository. They are entered once in the HA UI and live in HA's own gitignored storage. Never commit a token.

The Roomba

The one integration that needs a human at the robot. In the HA UI: Settings → Devices & services → Add integration → iRobot Roomba, and enter the robot's IP (the iRobot app or your router shows it). When the flow asks for the password, make sure the robot is on its dock, then press and hold its Home button until it plays a tone; HA fetches the credential itself in that window.

Note the vacuum.* entity id HA creates, fill it into the commented vacuum:roomba entry in config/homes/local.yaml, uncomment, and restart. mix dobby.ha.verify should then show the robot with its battery.

Two test tiers

Replay runs on every mix test and in CI, and is incapable of reaching a model provider; the test configuration guards it. It runs the whole application against the fake HA: one registry, one set of agents at fixed ids, scenarios taking turns. It is the tier that proves the machinery.

Eval (mix test --include eval) asks whether a real model exercises judgment, with real inference and real money. It is the only tier that can catch a tool contract that lies to the model, a prompt that permits fan-out on an ambiguous request, or a model echoing input framing into what a person reads. It has caught all three. Rotating models is part of the test.

mix test                      # replay: no HA, no network, no model calls
mix test --include eval       # eval: real inference
mix precommit                 # compile --warnings-as-errors, unused deps, format, test

The standard for a fixture: if it seeds what production builds, the test is lying. Ask of every one whether production does this, or whether the test is faking it.

A door for the agent working on Dobby

In development the running server also serves Tidewave at /tidewave/mcp, loopback only: evaluate code in the live node, read its logs, query the database. It is the complement of the MCP door: that one is for an agent working through Dobby on the house; this one is for an agent working on Dobby. Register it once:

claude mcp add --transport http tidewave http://localhost:4000/tidewave/mcp

What you should see

get_logs, get_source_location, get_docs, project_eval, execute_sql_query, browser_eval, create_design_canvas

Tidewave's tools, from tools/list. A request with a browser origin is refused, and a request from another machine is refused even when the server is bound to the LAN.

Reading the repository

CLAUDE.md at the root is the map: where things live, the rule the codebase is built around, and the conventions. Module documentation explains why a thing is the way it is and what was rejected, which is the house style and the reason the design survives a new reader.
