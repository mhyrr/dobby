The house file

One YAML file says what the house contains and what the box it runs on should do. You own it, Dobby writes it too, and it stays safe to share because no secret ever appears in it.

In development it is whichever file DOBBY_HOME_MANIFEST names. In an install it is /opt/dobby/config/home.yaml, so it needs no path override. Start from the example, which carries a comment on every section:

cp config/homes/example.yaml config/homes/my-house.yaml

The file has two top-level sections. house: is the house; system: is the box. This page walks the shape; the example walks the words.

The house

A short id and a name, the timezone every clock in the thread is read in, where Home Assistant is, and one entry per device.

house:
  id: my-house
  name: Our House
  timezone: America/New_York

  home_assistant:
    url: env:DOBBY_HA_URL
    token: env:DOBBY_HA_TOKEN

  devices:
    # …one entry per device, below…

Credentials are references, never values. token: env:DOBBY_HA_TOKEN names an environment variable; Dobby reads it at boot. A variable that is missing stops the boot with a sentence naming exactly which one; it does not start a house that cannot reach anything. That one rule is what keeps the file shareable: you can commit it, post it, hand it to an agent.

A device entry

Every device has the same six parts, and the device's own type decides what bindings and settings may contain.

KeyWhat it is
idHow Dobby refers to it, forever. Convention is type:place: thermostat:hall, light:kitchen. Renaming a device is making a new one.
typeOne of the types the house knows: thermostat, light, vacuum, wifi_endpoint.
nameWhat the household calls it, in the words they actually say.
aliasesThe other words they use for the same thing. "The thermostat", "downstairs".
bindingsWhich Home Assistant entity is which part of this device. The keys are the type's; the values are HA's entity ids, copied exactly.
settingsHousehold policy: what this house is willing to have asked for. Optional, and it can only narrow what the hardware already allows.

Entity ids live in Home Assistant under Settings → Devices & services → Entities. Use them exactly as HA names them. A device bound to an entity that does not exist boots as NOT KNOWN and stays that way; the verify task names it.

The four types

thermostat

A thermostat Dobby can read and set. One binding, climate, pointing at a climate.* entity. The range the hardware allows is discovered from the device itself (HA reports it), and settings only narrows that to what this household wants askable.

- id: thermostat:hall
  type: thermostat
  name: hall thermostat
  aliases: [the thermostat, downstairs thermostat]
  bindings:
    climate: climate.hall
  settings:
    min_temperature_f: 60
    max_temperature_f: 78

Policy narrows and never widens. With the range above, nobody can set the hall to 90: not a person at a card, not the model, not an agent over MCP. The refusal comes from the device agent in the same words whoever asked will read: the device says HELD, and the reason beside it names the range.

light

A light Dobby can switch, and dim if the bulb says it dims. One binding, light. Whether it dims is discovered from the bulb's supported colour modes, never declared here, so there is nothing to set.

- id: light:living_room
  type: light
  name: living room light
  aliases: [living room lamp]
  bindings:
    light: light.living_room

vacuum

A robot vacuum Dobby can start and send home. One binding, vacuum.

- id: vacuum:downstairs
  type: vacuum
  name: robot vacuum
  aliases: [the vacuum, the roomba]
  bindings:
    vacuum: vacuum.downstairs

wifi_endpoint

Something on the network Dobby can tell you the reachability of, and only that: a printer, a television, a speaker. Read-only on purpose. One binding, connectivity, usually a binary_sensor.* from HA's ping integration. That is what ha_integration records: a note for whoever reads the file, not a switch.

- id: wifi:office_printer
  type: wifi_endpoint
  name: office printer
  aliases: [the printer]
  ha_integration: ping
  bindings:
    connectivity: binary_sensor.office_printer

An endpoint going quiet at three in the morning is weather, not an event. It shows on the card and in the log, and it does not post a line into a thread somebody reads over breakfast.

The system section

The box rather than the house. Everything here is optional, and three of the four have a matching environment variable that wins while it is exported, so a one-off experiment never means editing the file.

system:
  # Which model answers. Unset means the committed default, which needs an
  # Anthropic key. Any provider ReqLLM speaks, as provider:model.
  model: openai:gpt-5.6-luna

  # The port the surface is served on.
  port: 4000

  # Bind every interface and advertise the name below, so anyone at home
  # can open http://dobby.local:4000/.
  lan: true
  hostname: dobby.local
KeyOverrideTakes effect
modelDOBBY_MODELAt the next reply. No restart.
portPORTWhen Dobby restarts.
lanDOBBY_LANWhen Dobby restarts.
hostname—When Dobby restarts. One DNS label and .local; it belongs to the LAN advertisement, not to Phoenix's public URL.

The same four knobs are a form on /admin, drawn from this section's own schema. A save there says, per field, whether it took effect now or is waiting for a restart.

Dobby writes this file too

Four surfaces end in this one file: an editor, the forms on /house and /admin, Dobby proposing a device in the thread, and an agent of yours over MCP. All of them go through one writer, so the file has a single author and two people saving at once is a queue rather than a race. The write is a temporary file beside the real one and an atomic rename: the next boot sees the old file or the new one, never half of either.

Two consequences worth knowing before you hand-edit:

  • Hand edits are welcome, and take effect when Dobby restarts. Dobby does not watch the file.
  • When Dobby writes, it rewrites the whole file. Your comments and key order do not survive; the file is the record, not the document. Keep your own notes somewhere else, or accept that the first save from a form will tidy them away.

What you should see

# This file is written by Dobby, and rewritten in full every time the # house or the system panel is changed. Comments and key order do not # survive that — the file is the record, not the document.

The header Dobby puts on a file it has written, verbatim. If your file starts with it, something other than your editor has saved it since.

Keep it a data file. A house described in Elixir (.exs) still boots (the test rig is one), but Dobby will not write one back, and every editing surface will say so rather than offer a form that could only be refused.
