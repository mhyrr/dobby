Your own agent

You do not have to do the setup in Dobby's chat. Dobby serves its tools over MCP at /mcp, so the AI you already use can do the work.

Mint a token

On /admin, in the System section, mint a token with a label for the agent that will hold it: Ann's laptop, the kitchen Mac. Every call made with the token is logged under that label. The token is shown once.

What you should see

Ann's laptopminted Aug 22, 2026

And beneath it, once: The token for Ann's laptop is ‹43 characters› — copy it now. Dobby keeps only a fingerprint, so it will not be shown again.

revoke closes the door. The next request with that token gets the same 401 as a made-up one. There is no undo; mint a fresh token.

Connect your agent

For Claude Code, one command:

claude mcp add --transport http dobby http://192.168.1.20:4000/mcp \
  --header "Authorization: Bearer <the token>"
Use the address, not the name Claude Code's MCP client (2.1.240, August 2026) does not resolve .local names. It times out. Use the address Dobby prints at startup: the house answers at http://dobby.local:4000/ (192.168.1.20). Any MCP client that speaks streamable HTTP connects the same way.

What you should see

$ claude mcp list dobby: http://192.168.1.20:4000/mcp (HTTP) - ✔ Connected

What it can do

Everything Dobby's own model can: read and set devices, write schedules, discover, propose, and confirm. The tool list is your house's. A house with no vacuum offers no vacuum tools. Every call runs the same checks and gets the same refusals as the thread.

What you should see

confirm_device, create_schedule, delete_schedule, discover_entities, light_get_status, light_set_brightness, light_turn_off, light_turn_on, list_schedules, propose_device, set_schedule_enabled, thermostat_get_status, thermostat_set_temperature, wifi_get_status

The tools of a house with a thermostat, a light, and a printer.

The trust

Whoever holds a token speaks for the household, the same way anyone with the Wi-Fi password does. That includes confirming a device into the house. Dobby does not defend against a stolen token. Home Assistant takes the same stance with its own long-lived tokens. What the token adds is a name, so the log says which agent asked.

A real session

August 22, 2026. Claude Code, pointed at a running house, asked to adopt one light. The tool calls and results are verbatim. The prose between them is Claude's.

  • Claude

    Step 1: discover_entities.

    discover_entities → 12 entities, among them light.kitchen_lights · type light · Kitchen Lights

  • Claude

    light.kitchen_lights is listed with type light. Step 2: propose_device.

    propose_device(id light:kitchen, type light, name "kitchen lights", entity light.kitchen_lights) → proposal 1 · proposed · proposed_by "Maya's walkthrough"

  • Claude

    Proposal id 1 returned. Step 3: you've agreed to this specific proposal, so confirming it.

    confirm_device(1) → applied: true · "written to the house file; the house has taken it on"

  • Claude

    Applied. Step 4: re-discover, then read the light's status.

    discover_entities → 11 entities; light.kitchen_lights no longer among them

    light_get_status(light:kitchen) → available · on · 71% · dimmable

Between the third and fourth calls, Dobby wrote the file and restarted the house. It answered only when the new device was running. The agent's connection survived the restart.

Tell it what you have

"Dobby at 192.168.1.20:4000 runs my house. I have a thermostat, three lights, and a robot vacuum, all on Home Assistant. Set them up." The agent discovers what Home Assistant sees, proposes each device, and confirms them. The house restarts into its new shape, and the cards fill in as Home Assistant reports.
