Growing the house

Four ways to add a device, and one file they all land in. Nothing enters the house unblessed: a device is proposed, somebody says yes, and only then is it written down.

Four ways, one file

  1. Say it. "What does Home Assistant have that we don't?" Dobby reads the entities Home Assistant knows and the house does not, and proposes an entry for the one you name. Nothing changes until you say yes.
  2. The cards. On /house, every card has edit and remove, and the foot of the list has add a device. The form's fields come from the device type's own schema, so a thermostat asks for its range and a light asks for nothing. A refused value is refused in the words the file would use, naming the field.
  3. The file. Edit home.yaml and restart Dobby. See The house file.
  4. Send your own agent. Any MCP client holding a key minted on /admin can do everything the first way does. See Your own agent.

All four go through the same writer and the same validation. A device that would not boot from a hand-typed file is refused at the form, in the thread, and over MCP, in the same sentence.

Proposed is not done

When Dobby or an agent adds a device, it happens in two steps, and the gap between them is the point. A proposal is a row Dobby has validated (the entity exists, it is not already bound, the id is free, the type knows what to do with it) and written nowhere. It has a number. A confirmation is somebody saying yes to that number; only then does the writer put the entry in the file and restart the house into its new shape.

Dobby reports a proposal as proposed and an applied change as applied, and it will not blur them. "I've added the kitchen light" before the confirmation lands is the same lie as "the room is warm now", and the doctrine forbids both.

What you should see

{"applied":false,"proposal":{"id":1,"device":"light:kitchen","name":"kitchen lights", "type":"light","status":"proposed","proposed_by":"Maya's walkthrough", "entry":{"id":"light:kitchen","type":"light","name":"kitchen lights", "aliases":["the kitchen light"],"bindings":{"light":"light.kitchen_lights"}}}}

A proposal as the tool returns it: applied: false, a number, and the exact entry that would be written. In the thread, Dobby says it in a sentence; over MCP, your agent sees this.

The whole house in one breath

You do not have to walk it one device per exchange. Stand next to a working Home Assistant and tell Dobby what you have: "the thermostat, these four lights, the vacuum, the printer, all on HA". It asks discovery once, proposes every entity it showed that matches what you named, and presents the proposals as one numbered list. One yes to the list is agreement to everything on it, and Dobby confirms each in turn.

Two things it will not do. It will not propose something discovery did not show. Anything you named that Home Assistant cannot see, it says it cannot see, because a yes to the list is not a yes to a guess. And it will not call the list done until every confirmation has applied; each entry stays proposed until its own yes lands.

However many devices are confirmed in one turn, the house restarts once. The writer coalesces.

The moment after

After any of the four ways, the new device reads NOT KNOWN for a moment. That is honesty, not breakage: the house has a new agent and it has not yet heard from Home Assistant. The first state sync fills it in.

What you should see

kitchen lightsNot known
kitchen lights71%Set

The same row a second or two apart: first the house admitting it does not know, then Home Assistant's answer.

Removing one

remove on a card asks once, in place (Remove kitchen lights?, with remove and keep it), and then the entry leaves the file and the house restarts without it. There is no undo line after a removal; adding the device back is the way back.
