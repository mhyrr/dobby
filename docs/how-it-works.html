How it works

Enough of the machinery to predict what Dobby will do before you ask it. The full design record is in the repository; this is the tour.

Two layers, one line

Dobby is two layers with a hard line between them.

Below the line is the deterministic layer: one small program per device, called a device agent, plus the Home Assistant client, the scheduler, and the writer that owns the house file. This layer owns every fact and every action. It knows what a thermostat's range is because Home Assistant told it; it knows what the household allows because the file said so; and it is the only thing that ever sends a command to Home Assistant.

Above the line is the language layer: one long-lived model-backed agent that holds the conversation. It can do exactly one thing to the house: call a tool from a closed set the device agents advertise. That set is a construction fact, not a prompt instruction: there is no path from the model to Home Assistant, to the network, or to arithmetic, because none was built.

Everything else on these pages follows from that arrangement.

Why it cannot say the room is warm

When you ask for 72, the model calls thermostat_set_temperature. The tool hands the request to the hall thermostat's agent. The agent validates it (is 72 inside the hardware's range and the household's?) and if so emits a description of a service call, which the runtime performs against Home Assistant. What comes back to the model is accepted: the command was valid and it was sent.

What the room does next arrives later, on its own, as a state change from Home Assistant, and lands on the board as a word. The model never sees it in the same breath, so it cannot report it. "The living room is warm now" is exactly the sentence this architecture exists to make impossible; "set to 72" is the most it can truthfully say, and it is what it says.

The same shape holds for a refusal. The agent that declines 85 in a house capped at 78 returns its reason; the tool carries it up unchanged; the model repeats it. The words you read are the device's.

The model knows what it is told

Before every message, the model is handed a block listing every device in the house with its id and its last known state. Those ids are the only ones that exist. A device not in the list is a device Dobby does not have, and the doctrine tells it to say so rather than guess. Ambiguity, two devices a phrase could mean, is a question back, because the doctrine forbids acting on several when one was asked for.

The doctrine is in code, composed after the soul. The soul can make Dobby warm or curt; it cannot give it permission to invent a device.

The house works when the model does not

A card on /house reaches a device with no model involved: a tap is a command to the device agent, directly. A schedule fires the same way: a timer wakes a deterministic process that calls the agent, and no model runs. These are first-class paths, not fallbacks: they are the test surface, and they are what the house does when the model is down, slow, or expensive. You will notice the difference: a card tap is effectively instant, and a sentence takes a couple of seconds.

Why the house restarts

The house is a supervision tree: one agent per device, started from the file at boot. Changing the house (adding a device, removing one, editing its bindings) means a different tree. So a change to the house file, from any of the four ways, is applied by restarting that tree into its new shape. It takes about a second; every device reads NOT KNOWN until Home Assistant speaks again; the thread and the rest of the application stay up.

That restart is why there is one writer. Three browsers saving three forms would otherwise write three files, and the last to finish would win an argument nobody had. Every path that changes the house goes through the same process, so saves queue rather than race, and the file is written whole or not at all.

Not everything needs a restart. The system section is honest about which of its knobs take effect now (the model alias does) and which belong to a socket opened at boot and wait.

Proposals

A device enters the house in two steps because the yes has to be a person's. Discovery reads what Home Assistant has that the house does not; a proposal is a validated, numbered entry written nowhere; a confirmation applies it. In Dobby's own chat the confirmation is your yes in the thread. Over MCP it is the agent calling confirm_device, and on that path holding the key is the yes; see the trust.

The fake Home Assistant

The Home Assistant client is one module behind one boundary, and the default implementation is a fake that lives in the repository. The entire test suite, and mix phx.server with no house file named, run against it: no HA, no network, no model calls. The real client is opt-in through configuration. That is why a developer can build, click and screenshot the whole surface on a train, and why verify exists: it is the one command that swaps the real client in and proves the wiring.

The record

For the reasoning behind all of this, and the alternatives that were rejected, the repository carries the design of record (dobby-design-jido.md), the surface's design system (DESIGN.md, which is binding), and the product thesis (PRODUCT.md). They were written for the people building Dobby, and they say why.
