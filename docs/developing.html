Developing

A real Home Assistant on your machine with virtual devices, two kinds of tests, and a door for the agent working on Dobby.

Two rigs

mix test, and mix phx.server with no house file named, run against a fake Home Assistant that lives in the repository. No HA, no network, no model calls. No environment variable changes that.

The second rig is a real Home Assistant in a container, for testing the real client: connection, token, subscription, service calls. It is disposable. Its state is gitignored, and remaking it costs two commands.

The local Home Assistant

Requires Docker.

cd dev/home-assistant
docker compose up -d

First boot takes a minute or two. The instance listens on http://localhost:8123. It runs configuration.seed.yaml, which turns on HA's demo integration: virtual thermostats (climate.hvac, climate.heatpump, climate.ecobee), lights, and vacuums.

Initialize it once. This creates the owner account, sets US units so HA reports in Fahrenheit, finishes onboarding, and mints the token Dobby logs in with. It prints the credentials and saves them nowhere.

mix run --no-start dev/home-assistant/onboard.exs
docker compose restart   # so every entity reports in °F

Point Dobby at it. config/homes/local.yaml is the house file for this rig. It takes its token from .env.

cp .env.example .env    # then fill in the token onboard.exs printed
mix phx.server

What you should see

[info] connected to Home Assistant 2026.8.2 at http://localhost:8123 home "local" with 4 device(s) %{ id: "thermostat:main", name: "demo thermostat", type: :thermostat, available: true, target_temperature_f: 70, min_temperature_f: 60, max_temperature_f: 76, current_temperature_f: 72, hvac_mode: :cool } … initial state sync: ok

From mix dobby.ha.verify against the rig, August 22, 2026. Running it shows the round trip.

To list what the instance has: Developer Tools → States in HA, or

curl -s -H "Authorization: Bearer $DOBBY_HA_TOKEN" \
  http://localhost:8123/api/states | jq -r '.[].entity_id'

Credentials for HA integrations (a cloud thermostat's account, a robot's password) go into the HA UI, not into .env or the repository. Never commit a token.

The Roomba

The one integration that needs a human at the robot. In HA: Settings → Devices & services → Add integration → iRobot Roomba, then enter the robot's IP. When the flow asks for the password, put the robot on its dock and hold its Home button until it plays a tone. HA fetches the credential in that window.

Fill the vacuum.* entity id HA creates into the commented vacuum:roomba entry in config/homes/local.yaml, uncomment it, and restart. Verify then shows the robot with its battery.

Two kinds of tests

Replay runs on every mix test and in CI, against the fake Home Assistant. It cannot reach a model provider. It proves the machinery.

Eval runs a real model, for real money. It asks whether the model exercises judgment. It has caught a tool description that misled the model, a prompt that let the model act on an ambiguous request, and a model echoing the prompt's framing into a reply.

mix test                      # replay: no HA, no network, no model calls
mix test --include eval       # eval: real inference
mix precommit                 # compile --warnings-as-errors, unused deps, format, test

A rule for fixtures: if a test seeds what production builds, the test is lying.

Tidewave

In development, the server also serves Tidewave at /tidewave/mcp, on this machine only. An agent working on Dobby's code can run Elixir in the live node, read its logs, and query the database. The MCP door is for an agent working on the house; this one is for an agent working on Dobby.

claude mcp add --transport http tidewave http://localhost:4000/tidewave/mcp

What you should see

get_logs, get_source_location, get_docs, project_eval, execute_sql_query, browser_eval, create_design_canvas

Tidewave's tools. Requests from a browser or from another machine are refused.
