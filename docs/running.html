Running it

Prove the wiring before you trust an evening to it, give Dobby a voice, and put the house on the Wi-Fi so every phone at home can reach it by name.

The environment

The house file names its credentials as env: references, so the environment has to answer them. Three variables cover a house: where Home Assistant is, the token for it, and a key for the model.

export DOBBY_HA_URL=http://homeassistant.local:8123
export DOBBY_HA_TOKEN=...
export ANTHROPIC_API_KEY=...

In development a gitignored .env saves re-exporting these per shell: copy .env.example and fill it in. Anything exported in the shell still wins over the file, and mix test ignores every one of these variables by design: the test suite runs against a fake Home Assistant and nothing in your environment can change that.

Verify, then run

mix dobby.ha.verify boots the real client against your HA and prints every device's snapshot once the first state sync lands. It is the one command that proves connection, authentication, subscription, routing and interpretation at once, device by device.

DOBBY_HOME_MANIFEST=config/homes/my-house.yaml mix dobby.ha.verify

What you should see

[info] connected to Home Assistant 2026.8.2 at http://homeassistant.local:8123 home "my-house" with 2 device(s) %{ id: "light:living_room", name: "living room light", type: :light, available: true, power: :on, brightness_percent: 71 } %{ id: "thermostat:hall", name: "hall thermostat", type: :thermostat, available: true, target_temperature_f: 70, min_temperature_f: 60, max_temperature_f: 78, current_temperature_f: 72, hvac_mode: :cool } initial state sync: ok

Every device available: true with readings. A device still unavailable after the sync window never got its entity's state; the task stops and tells you to check that entity id against Developer Tools → States.

--round-trip goes one step further and drives a thermostat through a one-degree setpoint change and back, waiting for HA's confirming state change each way. It aims at the first thermostat in the file unless you name one. It is a real change to whatever that entity controls, so name a virtual one if you have any doubt.

DOBBY_HOME_MANIFEST=config/homes/my-house.yaml \
  mix dobby.ha.verify --round-trip thermostat:demo

What you should see

discovered capabilities: %{min_temperature_f: 45, max_temperature_f: 95, hvac_modes: ["off", "heat", "cool", "auto", "dry", "fan_only"]} household policy: %{min_temperature_f: 60, max_temperature_f: 76} accepted range: 60–76 round trip: thermostat:demo setpoint 70 → 69.0 → back accepted 69.0; waiting for the house to confirm ... confirmed at 69.0 after 105ms accepted 70.0; waiting for the house to confirm ... confirmed at 70.0 after 104ms round trip: ok — setpoint restored to 70

Three lines of policy first (what the hardware allows, what the house allows, and the range that results), then two confirmations, each after HA reported the change. The milliseconds are your integration's: a virtual device answers in a hundred, a cloud-polled thermostat can take the length of its poll.

Then run it.

DOBBY_HOME_MANIFEST=config/homes/my-house.yaml mix phx.server

What you should see

[info] connected to Home Assistant 2026.8.2 at http://homeassistant.local:8123 [info] Running DobbyWeb.Endpoint with Bandit 1.12.4 at 127.0.0.1:4000 (http) [info] Access DobbyWeb.Endpoint at http://localhost:4000

Loopback only, until you say otherwise below. Open http://localhost:4000/ and the board is there with your devices on it.

The soul

config/soul.md is who is answering: voice, manners, what Dobby cares about. It is prose, and you edit it like prose. DOBBY_SOUL points somewhere else if you keep yours outside the repo; in an install it is /opt/dobby/config/soul.md.

The soul is personality and only personality. The rules that keep Dobby honest live in code: never invent a device, never act on a guess, report what was commanded rather than what was observed. They are composed after the soul, so a rewrite of the voice cannot delete a rule. Make it a grump or a saint; it still cannot tell you the room is warm.

The whole household

By default Dobby binds loopback: a house console has no business on the network before there is a house to console. When there is, set lan: true in the system section (or export DOBBY_LAN=1). Dobby then binds every interface and advertises the machine on the LAN as dobby.local for as long as the server runs, using dns-sd on macOS or Avahi on Linux.

What you should see

[info] Running DobbyWeb.Endpoint with Bandit 1.12.4 at 0.0.0.0:4000 (http) [info] the house answers at http://dobby.local:4000/ (192.168.1.20)

The name and the address, in the boot log. Every phone and tablet on the Wi-Fi can now open the name. Keep the address: it is what an agent that cannot resolve .local names will need; see Your own agent.

Port 4000 is the portable default. A bare http://dobby.local/ needs port 80, which on macOS is unprivileged (PORT=80 works as-is) and on Linux needs a reverse proxy or a service capability.

The trust model, stated plainly: the Wi-Fi password is the boundary. Anyone on the network is the household. There is no login, /admin is a room in the house rather than a privilege level, and every surface updates live for everyone. Do not put the LAN bind on a network you would not hand the Wi-Fi password to.

Running as an installed service

Not yet walked What follows is what the code is built to do, read from config/runtime.exs. Nobody has stood a release up on a box in a closet and written down what happened. When that walk is taken, this section becomes a page. An always-on box is the plan for it.

A release looks for the two files at /opt/dobby/config/home.yaml and /opt/dobby/config/soul.md, so it needs no path override for either. The referenced HA and model credentials, DATABASE_URL and SECRET_KEY_BASE stay in the service environment. The release keeps the same HTTP contract as development: loopback unless system.lan is true, and then the trusted LAN at the hostname and port in the house file. Put a real TLS reverse proxy in front before exposing it beyond that network; Dobby does not pretend an HTTPS listener exists.
