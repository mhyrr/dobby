Dobby

A house elf for your Home Assistant. Everyone at home talks to it in one shared thread, and it answers by doing things: reading the thermostat, dimming a light, starting the vacuum, setting a schedule for eight o'clock.

Dobby is a household agent. It runs on a machine in your house, next to Home Assistant, and the household reaches it from any phone or laptop on the Wi-Fi. You describe the house in one file, give it a voice in another, and it runs the house: it holds standing intentions, says plainly when a device refuses, and never claims something happened that did not.

Underneath are two layers with a hard line between them. A deterministic layer of device agents owns every fact and every action. Above it sits a language model that can act only through the closed set of tools those agents offer. The model never touches Home Assistant, never does arithmetic, and never says a room got warm. It reports what it commanded; the house reports what actually happened. How it works tells that story at the depth a user needs to predict Dobby's behaviour.

This guide is for a person with a working Home Assistant and a weekend. Every page was written from a walk somebody actually took, and where a thing has not been walked yet, the page says so.

What you need

  • A Home Assistant you can reach, and a long-lived access token for it. In HA, open your profile → Security → Long-lived access tokens and create one. It is shown once; put it straight into your environment.
  • Elixir 1.18 or later and PostgreSQL. mix setup installs the dependencies and creates the database.
  • A model API key. Unset, Dobby uses the committed default, which needs an Anthropic key. system.model in the house file swaps providers without a rebuild, to any provider:model ReqLLM speaks.
  • mDNS on the box, for the household name. macOS has dns-sd built in. On Linux, install and run Avahi (avahi-daemon and avahi-utils) so Dobby can publish dobby.local.

The five-minute path

Clone the repo, copy the example house, and make it yours. The example explains itself: every section carries the comment you would otherwise look up in The house file.

git clone https://github.com/mhyrr/dobby.git && cd dobby
mix setup
cp config/homes/example.yaml config/homes/my-house.yaml
# edit it: your HA's address, your devices

Export the credentials the file refers to, then verify before you trust. mix dobby.ha.verify boots the real client against your HA and prints every device's snapshot once the first state sync lands.

export DOBBY_HA_URL=http://homeassistant.local:8123
export DOBBY_HA_TOKEN=...
export ANTHROPIC_API_KEY=...

DOBBY_HOME_MANIFEST=config/homes/my-house.yaml mix dobby.ha.verify

What you should see

[info] connected to Home Assistant 2026.8.2 at http://homeassistant.local:8123 home "my-house" with 2 device(s) %{ id: "light:living_room", name: "living room light", type: :light, available: true, power: :on, brightness_percent: 71 } %{ id: "thermostat:hall", name: "hall thermostat", type: :thermostat, available: true, target_temperature_f: 70, min_temperature_f: 60, max_temperature_f: 78, current_temperature_f: 72, hvac_mode: :cool } initial state sync: ok

available: true with readings proves connection, authentication, subscription, routing and interpretation in one line per device. A device that stays unavailable has a wrong entity id, and the task names it.

Then run it, and open it.

DOBBY_HOME_MANIFEST=config/homes/my-house.yaml mix phx.server

What you should see

hall thermostat70°Cooling
living room light71%Set
office printerAwake

At http://localhost:4000/: the board with your devices on it, each one a reading and a word on a flap, and the thread beneath. The reading is what was set; the word is what the house reported. For a moment after boot a device reads NOT KNOWN, which is the house learning what it has; the first state sync fills it in.
