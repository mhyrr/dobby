The house, written down

Dobby's understanding of the house is not hidden in a model prompt. It has an explicit source of truth.

One house model, four ways to write it

The shared thread, the forms on /house and /admin, an outside agent over MCP, and a text editor can all change the same model. One writer validates and serializes every application change.

YAML is the current durable representation. It records which devices Dobby manages, what the household calls them, how they bind to Home Assistant, which settings narrow their capabilities, and how the Dobby server should run. The file never holds a secret, so you can share it.

In development, DOBBY_HOME_MANIFEST names the file. In an install it is /opt/dobby/config/home.yaml. Start from the example:

cp config/homes/example.yaml config/homes/my-house.yaml

Two sections. house: is your house. system: is the box Dobby runs on.

The house

house:
  id: my-house
  name: Our House
  timezone: America/New_York

  home_assistant:
    url: env:DOBBY_HA_URL
    token: env:DOBBY_HA_TOKEN

  devices:
    # …one entry per device, below…

Credentials are references. token: env:DOBBY_HA_TOKEN names an environment variable. Dobby reads it at boot. If the variable is missing, Dobby stops and names it instead of starting a house that cannot reach anything.

A device entry

Every device has the same parts. Only id, type, name, and bindings are required.

KeyWhat it is
idHow Dobby refers to it, forever. Convention: type:place, like thermostat:hall.
typeOne of the semantic types below. A type describes what the device means in the house, not who made it.
nameWhat the household calls it.
aliasesOther names people use for it: "the thermostat", "downstairs".
bindingsWhich Home Assistant entity is which part of the device. Copy entity IDs exactly.
hands_onlyOptional. Set true when Dobby and agents over MCP may read the device but may not command it. Card controls and schedules made in /admin still work.
settingsHouse rules. Optional. They can narrow what the hardware allows, never widen it.

Entity ids are in Home Assistant under Settings → Devices & services → Entities. A device bound to a wrong id shows NOT KNOWN and stays that way. Verify names it.

hands_only names the authority that remains. It does not mean the device is absent or globally read only. The language layer can still answer status questions. The command gate lives in the shared device protocol, so the same refusal applies to Dobby's model, MCP, and a delayed schedule they authored.

The device types

Home Assistant owns brands, accounts, radios, and protocols. Dobby owns the household contract. A Sonos room and a Cast speaker are both speaker. A Ring and a Reolink doorbell are both doorbell. Add one device entry for each household object you want Dobby to manage.

Some Home Assistant devices expose several entities. Keep them in one Dobby entry. A doorbell can bind its ring event, camera, and motion sensor. An environment monitor can bind temperature and humidity. Discovery proposes the complete binding map when Home Assistant says those entities share one device.

thermostat

Dobby reads it and sets it. The hardware's range comes from Home Assistant. settings narrows that range to what your house allows anyone to ask for.

- id: thermostat:hall
  type: thermostat
  name: hall thermostat
  aliases: [the thermostat, downstairs thermostat]
  bindings:
    climate: climate.hall
  settings:
    min_temperature_f: 60
    max_temperature_f: 78

With this range, nobody can set the hall to 90. Not a person at a card, not the model, not an agent over MCP. The thermostat shows HELD with the reason beside it.

light

Dobby switches it, and dims it if the bulb can dim. The bulb reports that itself. Nothing to set.

- id: light:living_room
  type: light
  name: living room light
  aliases: [living room lamp]
  bindings:
    light: light.living_room

The action limit is part of each type. It does not depend on the model behaving well. Locks cannot be unlocked, access covers cannot be opened, and safety sensors cannot be actuated through the thread, a schedule, or MCP.

vacuum

Dobby starts it and sends it home.

- id: vacuum:downstairs
  type: vacuum
  name: robot vacuum
  aliases: [the vacuum, the roomba]
  bindings:
    vacuum: vacuum.downstairs

wifi_endpoint

Something on the network Dobby can report as reachable or not: a printer, a TV, a speaker. Read only. The usual source is a binary_sensor from Home Assistant's ping integration.

- id: wifi:office_printer
  type: wifi_endpoint
  name: office printer
  aliases: [the printer]
  ha_integration: ping
  bindings:
    connectivity: binary_sensor.office_printer

A printer that drops off at three in the morning shows on its card and in the log. It does not post into the thread.

The system section

All six settings are optional. Three have an environment variable that wins while it is exported, so you can try something without editing the file.

system:
  model: openrouter:openai/gpt-5.6-luna
  reasoning: low
  routing: latency
  port: 4000
  lan: true
  hostname: dobby.local
KeyOverrideTakes effect
modelDOBBY_MODELAt the next reply. OpenRouter names use openrouter:author/model. Two have been walked: openai/gpt-5.6-luna, the default, and z-ai/glm-5.3-flash.
reasoning—At the next reply. How hard a reasoning model thinks before it answers: low, medium or high. Unset leaves the provider's default.
routing—At the next reply. What OpenRouter optimizes for when it picks the endpoint that serves the model: latency, throughput or price. It is an OpenRouter setting, so it needs a model reached through OpenRouter: set it beside a model that is not an openrouter: name and the house refuses to start, saying so. That is deliberate — the alternative is a house that starts and then cannot answer anything.
portPORTOn restart.
lanDOBBY_LANOn restart. Binds every interface and advertises the hostname.
hostname—On restart. One label and .local.

GLM 5.3 Flash is the fast choice, and only with reasoning: low and routing: latency: on the day it was measured, its first word arrived in under a second where Luna took one to three, and a reply cost about the same on either. Luna stays the default because Dobby is built and tested against it first.

The same six settings are a form on /admin. After a save, each field says whether it took effect now or waits for a restart.

Dobby writes this file too

The forms on /house and /admin, a device Dobby proposes in the thread, and an agent over MCP all write to this file. One writer handles every change, so two saves at once queue instead of colliding. Two things to know before you edit by hand:

  • Hand edits take effect when Dobby restarts.
  • When Dobby writes, it rewrites the whole file. Your comments and key order do not survive.

What you should see

# This file is written by Dobby, and rewritten in full every time the # house or the system panel is changed. Comments and key order do not # survive that — the file is the record, not the document.

The header Dobby puts on a file it has written. If your file starts with it, something other than your editor has saved it.
